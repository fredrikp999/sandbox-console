Proposal · ACP client for OpenShell sandboxes

Sandbox Console

A local web app that lists your OpenShell sandboxes and lets you work with the agent in each one over ACP. The agent stays inside its sandbox. The console only shows what it does and asks you before it acts.

Interactive mockup with example content. Click a sandbox, type / in the message box, answer the permission request.

    How the screen maps to ACP

    Every element is one protocol message

    The console needs nothing from the agent beyond what ACP already sends. The OpenCode agent in your sandbox already reports models, commands, plans, tool calls and permission requests; acp_client.py prints the same messages as text.

    On screenACP messageNotes
    Sandbox list and status pillsopenshell sandbox listNot ACP. Polled by the bridge every few seconds. Ready, starting and stopped get their own pill.
    Opening a sandboxinitialize → session/newThe bridge spawns openshell sandbox exec … opencode acp. Past sessions can be reopened with session/load (OpenCode supports it).
    Model pickerconfigOptions · session/set_config_optionThe list arrives with session/new; about 400 models on OpenRouter, so the picker needs search.
    Slash menuavailable_commands_updateAgent commands (/init, /review) plus a few console commands.
    Streaming replyagent_message_chunkRendered as Markdown. Thoughts (agent_thought_chunk) fold into a “Thinking” line.

    Permission cardsession/request_permissionButtons are the agent's own options (allow once, always, reject).

    Architecture

    A small bridge on your machine

    A browser can't start processes, so a local bridge does it. It runs one sandbox exec per open session and relays ACP between that process and the browser over a WebSocket. No port is opened in the sandbox.

    Security rules the console keeps

    • Advertise no fs or terminal capability. The agent works only inside the sandbox.
    • Bind to 127.0.0.1, with a random token in the URL, so other local users and web pages can't drive your agents.
    • No credentials in the console. Providers stay in the gateway, as now.
    • Code leaves through git bundles you review, as in the README.

    Why the bridge is needed

    • Keeps sessions alive when you close the tab, and replays them when you come back.
    • Several sandboxes at once, one agent process each.
    • Adds the parts ACP doesn't cover: sandbox list, create, delete, and network events from openshell logs.
    Recommendation

    Build it as a local web app first

    I recommend a Node bridge with a React front end, started with one command such as ./console.sh. It reuses what acp_client.py already proved works. A desktop wrapper (Tauri) can come later without changing the bridge or the UI.

    Phase 1

    Chat with one sandbox

    Sandbox list, open a session, streaming replies, tool cards, permission cards, stop. About the scope of acp_client.py.

    Phase 2

    Work across sandboxes

    Several live sessions, model picker, slash menu, session history with session/load, create and delete sandboxes from the UI.

    Phase 3

    Review and ship

    Files changed with diffs, git bundle download, a network view built from openshell logs (still to check that the logs carry policy denials), Claude Code once its ACP adapter is in the image.

    Mockup content is example data. Sandbox names come from your current openshell sandbox list; the conversation, files and network counts are illustrative.
